# Архитектура: Knowledge Base → RAG → AI Agent

Документ описывает прототип и решения, которые за ним стоят. Код в репозитории реализует ту же схему: пайплайн настоящий, хранилище, эмбеддинги, реранкер и LLM заменены моками за портами.

## 1. Схема и границы

```
Knowledge Base                 RAG                                         AI Agent
(PostgreSQL + pgvector + FTS)  Query Understanding                         ответ + цитаты
  статьи, версии, секции  ──►  Pre-filter ──► Vector ─┐                    вызывается только
  чанки, эмбеддинги            (до поиска)   Full-Text ├─► RRF ─► Rerank ─►  при достаточном
  факты, claims, сущности                    Metadata ─┘          │        confidence
  топики, источники                                       Context Builder ──►
```

**Knowledge Base хранит и структурирует.** Статьи со всеми версиями, разбиение на секции и чанки, эмбеддинги, извлечённые факты и claims со статусом верификации, сущности, топики, источники с надёжностью. Здесь же живёт процессинг и его ошибки (в прототипе это экран Processing и упавшая на эмбеддингах статья).

**RAG ищет и собирает контекст.** Понимает запрос, сужает корпус фильтрами, ищет гибридно, реранжирует, решает, что именно увидит агент, и считает confidence.

**Agent отвечает.** Получает компактный контекст (в прототипе 5 чанков и несколько фактов вместо всей базы) и обязан цитировать каждый тезис.

Почему это разные узлы:

- У них разный ритм изменений. База меняется при публикации и переобработке контента, RAG при настройке ранжирования, агент при смене модели и промпта. Смешивание означает, что правка промпта требует переиндексации, а это неприемлемо.
- У них разные метрики качества. Для базы это полнота и свежесть, для RAG recall@k и точность контекста, для агента faithfulness ответа. Оценивать их нужно по отдельности, иначе непонятно, где ломается.
- Агент не должен ходить в базу сам. Всё, что он видит, проходит через одну точку (Context Builder), поэтому её можно логировать, ограничивать по токенам и проверять.

## 2. Решения

**pgvector + FTS в одном Postgres вместо отдельной векторной БД.** Фильтры по project_id, языку, источнику, статусу верификации и датам живут рядом с векторами и текстом, всё выполняется одним запросом с одним планом. Отдельная векторная БД потребовала бы дублировать каждое фильтруемое поле и синхронизировать его. На объёмах пилота (десятки тысяч чанков) HNSW в pgvector справляется без проблем. Пересматривать решение стоит на сотнях миллионов векторов, не раньше.

**Префильтр до ANN, а не после.** Если искать ближайших соседей по всей базе и фильтровать потом, селективный фильтр (например, один язык) оставляет из top-20 два-три чанка, и recall незаметно проседает. В трейсе прототипа видно размер корпуса до и после префильтра и вклад каждого фильтра. Запрос 4 (язык TR) показывает предельный случай: после фильтров 0 чанков, пайплайн не падает и честно отказывает.

**Гибридный поиск с RRF.** Векторы ловят перефразировки, BM25 ловит точные токены вроде `TRC-20` или `AccountPermissionUpdate`, которые эмбеддинги размывают. RRF сливает ранги, а не скоры, поэтому не нужно калибровать две несравнимые шкалы. k = 60 стандартное значение, его стоит проверить на эталонном наборе.

**BM25 с IDF как в Lucene, а не Okapi.** Okapi-IDF `log((N − n + 0.5) / (n + 0.5))` равен нулю или отрицателен для термина, который есть в половине документов. После префильтра корпус часто сжимается до 5–15 чанков, и запросные термины вроде `multisig` выпадают из ранжирования. Lucene-вариант `log(1 + (N − n + 0.5) / (n + 0.5))` всегда положителен.

**Реранкер как отдельный порт.** Реранкер самый дорогой и самый заменяемый компонент: сегодня мок, завтра bge-reranker на своём GPU или Cohere Rerank. Порт фиксирует контракт (кандидаты на входе, скоры на выходе), остальной пайплайн о реализации не знает. Порог отсечения (`RERANK_MIN_SCORE`) относится к политике приложения и лежит в `application/config.py`, а не внутри адаптера.

**Context Builder как единственное место, которое решает, что видит агент.** Он отбирает чанки, подтягивает факты, выкидывает OUTDATED (если включён `exclude_outdated`), собирает источники и считает confidence. Если завтра понадобится лимит по токенам, маскирование PII или запрет на определённые источники, это делается в одном классе.

**Low confidence как явный путь, а не исключение.** Отказ отвечать это штатный тип ответа (`LowConfidenceResponse`) с причинами, возможными источниками и действиями: расширить фильтры, запросить верификацию фактов, создать рекомендацию по контент-гэпу. Агент в этом случае не вызывается: тест `test_run_rag_query.py` проверяет это через мок агента. Для SEO-платформы отказ ценен сам по себе: это сигнал, что в базе дыра.

**Все версии хранятся, индексируется только live.** История нужна для аудита и отката. В индекс попадает только live-версия, иначе поиск будет возвращать устаревшие формулировки рядом с актуальными. В прототипе версии видны в шапке документа.

**`project_id` везде с первого дня.** Каждая сущность несёт `project_id`, префильтр всегда применяет его первым. Мультитенантность, добавленная потом, означает миграцию каждой таблицы и аудит каждого запроса. Сейчас это одно поле.

### Формула confidence

`0.5 · rerank_mean + 0.3 · verified_share + 0.2 · source_diversity`, где `source_diversity = min(unique_sources / 3, 1)`. HIGH ≥ 0.75, MEDIUM ≥ 0.6, ниже LOW. Пороги и веса лежат константами в `application/config.py`.

Три уточнения, которых нет в исходной формулировке:

- `rerank_mean` считается по `max(число результатов, 3)` слотам: недостающие до минимума результаты учитываются как нули. Иначе два сильных чанка давали бы такой же rerank_mean, как пять.
- Если результатов меньше трёх, уровень принудительно LOW, даже когда формула даёт больше. Это то же правило, по которому агент не вызывается, и UI не показывает MEDIUM рядом с отказом.
- Если вопрос привязан к периоду, который не покрывает ни один чанк и ни один факт в контексте (в запросе указан 2027 год, а свежайшее свидетельство датировано 2026), уровень тоже принудительно LOW, а причина идёт первой в `reasons`. Найденные чанки могут быть релевантны теме, но прогноз из базы фактов не выводится. Запрос 2 показывает этот случай: формула даёт 0.70, ответ всё равно не генерируется.

## 3. Что замокано и как заменить

| Порт | В прототипе | В продакшене |
|---|---|---|
| `ArticleRepository`, `KnowledgeRepository`, `ProcessingRepository` | in-memory, читают `fixtures/*.json` | PostgreSQL, SQLAlchemy/asyncpg |
| `VectorSearchPort` | пересечение токенов запроса с `semantic_tags` чанка + косинус по TF-векторам | pgvector HNSW, `ORDER BY embedding <=> $1` внутри того же `WHERE`, что и префильтр |
| `FullTextSearchPort` | `rank-bm25` по тексту отфильтрованного корпуса (с IDF как в Lucene) | `tsvector` + `ts_rank_cd` или BM25 через расширение (pg_search / ParadeDB) |
| `RerankerPort` | `0.6 · fused_norm + 0.3 · entity_overlap + 0.1 · reliability` | bge-reranker-v2 (self-hosted) или Cohere Rerank |
| `AgentPort` | шаблонный ответ из фактов и чанков с маркерами `[n]`, токены `len // 4` | OpenAI Agents SDK за собственным интерфейсом |
| `LatencyModel` | детерминированные миллисекунды по размеру работы | реальные тайминги из трейсинга (OpenTelemetry) |

Все числа в трейсе вычисляются: другой запрос или другие фильтры дают другие кандидаты, скоры и confidence. Тайминги синтетические и детерминированные, чтобы экспортированный `traces.json` не менялся от запуска к запуску.

## 4. Спорные моменты для обсуждения

1. **Источник контента.** Раздел 5.1 ТЗ рекомендует экспорт из CMS, роадмап ставит краулер вторым шагом. Нужен один вариант на пилот. Экспорт из CMS даёт структуру и версии бесплатно, краулер видит то, что видит пользователь, но теряет историю. Предложение: CMS-экспорт на пилот, краулер как способ сверки.
2. **FTS для TR и UA.** В Postgres нет готовых конфигураций text search для турецкого и украинского. Предложение: для этих языков опираться на векторный поиск с бустом по совпадению сущностей и `simple`-конфигурацию FTS для точных токенов (тикеры, названия методов).
3. **Привязка к OpenAI Agents SDK.** Предложение: держать SDK за `AgentPort`, промпты версионировать (`prompt_version` уже есть в ответе), чтобы смена провайдера не трогала RAG.
4. **Веса confidence подобраны вручную.** Без эталонного набора из 50–100 вопросов с ожидаемыми ответами их нельзя откалибровать. Это нужно сделать до включения агента в контур, иначе пороги HIGH/MEDIUM ничего не значат.
5. **Статус CONFLICTING.** Кто разрешает конфликт: агент, редактор, или факт исключается из контекста до разрешения? Сейчас конфликтующие факты попадают в контекст и снижают verified_share (запрос 3 показывает это на мультиподписи). Предложение: исключать из контекста и ставить задачу редактору.
6. **Реранкер на каждый запрос.** Это основная статья стоимости и латентности (в трейсе это самая долгая стадия). Предложение: кэш по хэшу `(query_normalized, filters)` с TTL и инвалидацией при переиндексации затронутых статей.
7. **12 агентов в ТЗ против 5 на пилот.** Предложение: начать с пяти, у которых есть измеримый результат, остальные добавлять по мере появления эталонных наборов для них.
